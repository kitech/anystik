# qlstik 移植计划

> 权威规划文档。目标：`anystik`（QSkinny/Quick）业务功能 → Qt Widgets 桌面版 `qlstik`。
> 编译优先级：**Qt3 → Qt4 → Qt6**。
> 参考：`qldox/`→`../doxhttpd/qltox`（Qt3/4/6 范式 + **curl 异步引擎**）、`qlcomp/`（组件库）、`anystik/`（功能与行为基准）。
> 现状核实日期：2026-09-29（`qlstik/`、`stikcommon/` 均为空目录，anystik 侧未改动）。

## 1. 目标与范围

- 产出 `qlstik` 桌面应用，覆盖 anystik 全部桌面功能：贴纸家 / 生成 / 在线包 / 本地包 / 以图搜图 / 预览 / 编辑 / DAV 同步 / 查号 / 查 IP / 日志 / 登录 / 关于 / 设置 / 托盘 / 主题 / 语言 / 通知 / 存储迁移。
- **不移植 Android 专属模块**：`androidutils`、`android_tls_bootstrap`、`shareintentreceiver`、`keepalive`、`phonemonitor`、`phonesmsstatusbar`、`pushhandler`、`pushstatusbar`、`android/`、`build-android.sh` 及 APK 产物。
- 非 UI 逻辑**与 anystik 共用同一份实现**（共享层），不复制、不重写。
- 三套构建共用一个 `qlstik.pro`：`buildqt3.sh`（QTDIR=/opt/qt338sh）→ `buildqt4.sh`（qmake-qt4）→ `buildqt6.sh`（/opt/qt/6.7.3/gcc_64）。

## 5. 传输层：qltox curl 异步引擎（重点）

### 5.1 引擎能力盘点（`qldox/eventpoller.h` 401 行 + `.cpp` 341 行）

- `class EventPoller : public QThread`，静态单例：`start()` / `stop()` / `addRequest()`。
- 后端 `curl_multi`：独立泵线程 `curl_multi_poll(20ms)` + 每轮一次 `curl_multi_perform`，**真异步、不阻塞 GUI**。
- 请求体 `HttpRequest{url, method, data, timeoutSec, stallSec, lowSpeedLimit/Time, delayMs, extraHeaders, progress}`。
- 响应体 `HttpResponse{httpCode, curlErrStr, body, headers(map), elapsedMs}`。
- 健壮性已内建：停滞看门狗（boottime，休眠照算）、curl 原生低速中止、进度 100ms 节流 + 实测速率、非阻塞延迟重发队列、`pendingMutex` 保护 GUI↔泵线程交接。
- 跨线程投递范式（`restapi.cpp`）：回调内 `QApplication::postEvent(s_target, ev)`，事件类型用 `compatcore34.h` 的 `EventType34` / `CustomEventBase`（Qt3 可用）。
- Qt3 可用：已在 `qltox.pro` SOURCES/HEADERS（18/39 行）内，且 qltox 有 `build-qt3` 产物。

### 5.2 复用方式（零复制、不改 qltox）

- `stikcommon/qldox.pri` 收录 `$$QLDOX_DIR/eventpoller.cpp` + `eventpoller.h` → **EventPoller 直接编入 q3stik/q6stik**，不新建、不复制。
- qlstik 的 Qt3/4 网络垫片 = **QNAM 兼容面**（`compat/qt3/qnam_*`），其**后端换成 EventPoller**；不再另写 curl 引擎。
- 语义等价映射：`QNetworkAccessManager` ≈ EventPoller（单例）、`QNetworkReply` ≈ 一次 `HttpRequest` + 投递状态机。

### 5.3 QNAM 面 → EventPoller 映射

| QNAM 调用（共享模块实际用到） | EventPoller 侧 |
|---|---|
| `get/head/put/post(url)` | `addRequest(HttpRequest{url, verb, data, timeoutSec, extraHeaders})` |
| `sendCustomRequest` | 同上，`method` 传自定义 verb |
| `QNetworkRequest::setUrl/setRawHeader/setAttribute` | `HttpRequest.url` / `extraHeaders`（header 走 map） |
| `setTransferTimeout` | `HttpRequest.timeoutSec` |
| `reply->finished/readyRead` | `done` 回调 → `postEvent` 到 reply 所属线程 → 顺序 emit `readyRead` → `finished` |
| `downloadProgress(recv,total)` | `HttpRequest.progress`（节流已在引擎内） |
| `error()/errorString()` | `HttpResponse.httpCode` / `curlErrStr` 映射到 `NetworkError` |
| `rawHeader/hasRawHeader/header` | `HttpResponse.headers` map 查表 |
| `readAll()` | 句柄内累积 body（引擎回传完整 body；流式场景按需分块） |
| `abort()` | **软取消**（见 5.4-a） |
| `setCookieJar/cookieJar` | **qlstik 侧 cookie jar**（见 5.4-b） |
| `QHttpMultiPart/Part` | 手工拼 body + `Content-Type` 边界（见 5.4-c） |
| 同步惯用法（QNAM + QEventLoop） | 投递后在**本地** QEventLoop 等 `finished`（引擎在独立线程，不阻塞） |

### 5.4 三个必须 qlstik 自行解决的点（不改 qltox）

- **a. 取消**：`addRequest` 返回 void、无句柄取消 API → 软取消：`udata` 内放 `QCancelToken{atomic<bool>}`；`abort()` 立即置位并在本地线程 emit `aborted` + `finished`，句柄在 `done` 回调到达时自行销毁并静默丢弃数据（不重复 emit）。
- **b. Cookie**：`HttpRequest` 无 cookie 透传字段 → shim 内维护 `QNetworkCookieJar` 兼容类：请求前把 jar 中匹配 URL 的 cookie 拼成 `Cookie:` 头；响应后从 `headers` 里取 `Set-Cookie` 写回 jar。davbisync 依赖会话 cookie，此项**必须做对**。
- **c. multipart 上传**：`imagetmpuploader` 用 QHttpMultiPart → shim 侧 `QHttpMultiPart/QHttpPart` 拼 body 与边界头，`HttpRequest.data` 承载。
- 另：`readAll()` 一次性返回完整 body（引擎语义），大文件下载走 `progress` + 落盘回调，避免整包驻留。

### 5.5 生命周期与链接

- `main()`：`EventPoller::start()`；`qApp` aboutToQuit → `EventPoller::stop()`。
- `LIBS += -lcurl`（`curl_multi_poll` 需 libcurl ≥ 7.66，脚本里用 `curl-config --version` 校验）；`unix:!macx: -lX11`；`-ldl`；FreeType 走 pkg-config（emoji）。
- Qt3 分支照 `qltox.pro`：`isEmpty(QT_VERSION)` → `DEFINES += QT3_BUILD` + 手工 `QTDIR` 推导。

### 6.2 垫片的引入方式：显式条件 include（无聚合头、无 qt3camel）

- **不建** `qtcompat.h` 聚合头，**不做** `-include` 全局预包含，**不建** qt3camel 式软链映射。
- qlcomp 自身已是 Qt3 干净形态（`compat34.h` / `compatcore34.h` 全部走 `#ifdef QT3_BUILD` 小写头分支），所以壳层与 qltox 的 `cJSON` / `eventpoller` 在 Qt3 下零垫片可编。
- 垫片头放在 `stikcommon/`（平铺，按类名取名），**由共享模块文件自己的条件 include 引入**（属 §7 允许的「include / #ifdef ≤3 行/文件」改动）：

```cpp
// 共享模块内的标准写法（anystik 侧永远走不到 #else 分支）
#include "compat34.h"                 // qlcomp；Qt3 分支给 Qt3 小写头
#if QT_VERSION >= 0x050000
#include <QJsonDocument>              // Qt5/6 原生
#else
#include "shared/qjson_shim.h"        // qlstik 垫片（QLJSON 家族走 cJSON）
#endif
```

- 阈值约束：单个共享模块的条件 include 改造总计 ≤3 行/文件；超出即触发 §7 的「不可共享」判定。
- `QLNAM` 家族（Qt3 无）在 qlstik 侧落到 `stikcommon/qnam_shim.h`（受 `qt3/qt4/qt6` 三态开关；实际实现见 §6.3b），后端是 qldox `EventPoller`（§5）。
- 垫片只在 qlstik 构建的 INCLUDEPATH 内可见，anystik 构建不引用，**共享模块两侧行为完全一致**。

### 6.3e-1 批次 3c-1 落地记录：qnam_shim manager 信号层 + SSL 完整接受链（QWebdav 纳入移植范围）

**范围裁定（本日两次修订，最终版）**：
- 一度推翻「`qwebdav` 全家废止」并纳入移植范围（理由：`QWebdav : public QNetworkAccessManager`，底层仍走我们的垫片 → curl_multi）。
- **完整移植实测后按 §7 判「不可共享」，撤回该决定**（详见下方「§7 判定」）。`davbisync` 改用**窄切面自研**：只在 `qnam_shim` 之上实现 davbisync 真正用到的 13 个方法 + `errorChanged`。
- 本记录中**已落地且无论走哪条路都保留**的部分：manager 信号层、SSL 接受链、qsslprobe/qcabundle、新增的 QByteArray/QString/hex 垫片。

**§7 判定（为什么放弃完整移植）**：Qt3.5 有三个**不可垫片**的结构性障碍——
1. `QByteArray` = `typedef QMemArray<char>`，全局 typedef **无法加成员**（缺 `append`/`toHex`/`fromHex`/`number`/`(const char*)` ctor）；
2. `QString` 同理（缺 `size()`/`chop()`/`toUpper()`/`clear()`）；
3. Qt3 的 `QIODevice` **不继承 QObject**（`qiodevice.h` 无 QObject 基类），故拿不到 `QObject::deleteLater()`/父子关系/`sender()`，而 QWebdav 全程传 `QIODevice*` 并依赖 Qt4+ 的 QObject 生命周期语义。**注意**：这不是「Qt3 的 QObject 没有 deleteLater」——`QObject::deleteLater()` 在 Qt 3.5 就有（`qobject.h:174`），是 `QIODevice` 本身不是 QObject 才用不上。

三者都只能逐 call-site 改写，无法收敛。且已产生 3 处**语义**改动（非 include 包裹），按 §7「控制流/数据结构 0 行，任意 1 行 → 不可共享」已越线：
- `QMetaObject::invokeMethod(..., Qt::QueuedConnection, Q_ARG(...))` → 同步调用（延迟删除变同步删除）；
- `outDataDevice->deleteLater()` → `delete`（生命周期语义变）；
- `qobject_cast<QNetworkReply*>(QObject::sender())` → 垫片记的「当前派发中 reply」（数据来源变）。

代价还不止于此：继续改完意味着 `stikcommon/` 长期多一份**与上游分叉、无法 re-sync 的 vendor 副本**（2132 行），与「单一实现」初衷相反。故回滚。

**moc 事实澄清（保留，后续仍有效）**：
- 初判「Qt3 构建不跑 moc、vendor 信号须全去掉」**错误**。实测 `qlstik/qlstik.pro:19` `CONFIG += moc`、`:92` `QMAKE_MOC`；`qlstik/build-qt3/` 下确有 `moc_imagetmpuploader.cpp`/`moc_imageaiutil.cpp`/`moc_phonedb.cpp`。
- 但因最终改走窄切面自研，**vendor 的 `signals:` 无需 moc**（新写的窄切面类不声明 Q_OBJECT，信号走 `qconnect_slots` 垫片，与 QNAM 垫片同一套机制）。`qconnect_slots.h` 只服务于垫片的伪信号。

**已落地（Qt3 `/opt/qt338sh` 全绿，`g++ -fsyntax-only` error=0）**：

- `qnam_shim.h/.cpp` manager 层：新增 `finished(QNetworkReply*)`、`authenticationRequired(QNetworkReply*, QAuthenticator*)` 两个 PMF 伪信号 + `slots_finished()`/`slots_authRequired()` 注册表 + `notifyReplyFinished/notifyAuthRequired`；两个信号本体为**外部非 inline 定义**（取址地址须唯一，`&QNetworkAccessManager::finished` 才能与 reply 的区分）。这正是 `qwebdav.cpp:67-68` 连的那两个。
- `emitFinished()` 改为非 inline（前置声明的 manager 不完整），统一在 Qt4+ 语义点补 manager 通知，保证各条错误路径都覆盖——`QWebdav::replyFinished` 挂在 manager::finished 上收尾读数据。
- SSL 完整接受链（对齐 Qt4+ `sslErrors`/`ignoreSslErrors`）：`deliverResult` 识别证书类失败 → `qSslProbeSync` 真实探测 → 组 `QList<QSslError>` → `emitSslErrors` → 槽裁决；`ignoreSslErrors()` 则 `qCaBundleTrust` + `qCaBundleActivate` 后 `reissue(this)` 重发；用户 `abort()` 则标记「用户拒绝」不重试。`m_sslRetried` 防无限重试；`m_inSslDispatch` 区分「sslErrors 派发窗口内的用户 abort」与普通取消（否则会被误判成网络错误）。
- 401 → `notifyAuthRequired` → 填 `Authorization: Basic` 重发一次（`QWebdav::provideAuthenication` 依赖它）。
- `deleteLater()`：**一度误判「Qt3 QObject 无 deleteLater」而自造了 `QNetworkDeleteEvent`（`QEvent::User+122` + `event()` 自删），已删除**。`QNetworkReply` 继承真 `QObject`，直接用原生 `QObject::deleteLater()` 即可（`qobject.h:174`）；它依赖 DeferredDelete 事件，qlstik 有事件循环（`src/main.cpp:87 app.exec()`）故可用。自造版本不仅多余，还遮蔽了继承来的正确实现。
- `qconnect_slots.h`：① manager 发送者的两个重载；② reply `sslErrors` 重载；③ **PMF 槽绑定**（`qBindVoid/qBind1/qBind2`）——原先只吃 lambda，而 vendor 传的是 `&QWebdav::replyFinished` 这类成员函数指针；④ `disconnect` 宽容版（槽参数泛化）。
- `qlist_shim.h`：补**值语义** `append`；`qnam_shim.h` include 它，使 `QList<QSslError>` 与 vendor TU 同一类型。

**踩坑与决策（探针实测）**：
1. **`QList` 在 `qnam_shim.cpp` 里解析成了 `QPtrList`（宏）**，`errs.append(QSslError(...))` 报 "cannot convert to `const QSslError*`"。根因：Qt3 `QValueList` 本身就是**指针容器**，其 `append(T*)` 是指针版，而 `qlist_shim.h` 派生类未遮蔽成值版；且该 TU 未 include shim。两处都要修。
2. **`using ::connect;` 必须写在**函数体**首行，不能写在类作用域**（类作用域写 `using ::connect;` 是 "using-declaration for non-member at class scope" 编译错）。这与 §6.1 模式一致（`imagetmpuploader.cpp:272`、`imageaiutil.cpp:564`、`phonedb.cpp:101`）。
3. **`disconnect` 同样被 `QObject::disconnect` 成员遮蔽**，需在含 `disconnect` 的函数体首行加 `using ::disconnect;`（vendor `qwebdav.cpp:180-181` 收尾要解两个连接）。→ QWebdav 改造的三个收口点。
4. vendor 那处 `connect(reply, &QNetworkReply::sslErrors, this, &QWebdav::sslErrors)` **签名不成立**：槽多一个前导 `QNetworkReply*`（`(QNetworkReply*, const QList<QSslError>&)` vs 信号 `(const QList<QSslError>&)`），Qt 原生 PMF connect 同样不允许；且该 connect 在 vendor 里**从未被调用**（`QWebdav::sslErrors` 是死代码，anystik 也不调 pin 接受 API）。改造时按 `onSslErrors(const QList<QSslError>&)` 收口。
5. Qt3 `QByteArray`=`QMemArray<char>` 无 `(ptr,len)` 构造，Basic Auth 串改用 `QCString` + `resize/memcpy`。
6. 垫片无连接 id，`disconnect` 按「清空对应槽表」处理；`QWebdav` 每轮新建实例，语义等价。
7. `QWebdav::sslErrors` 的 pin 语义（`qwebdav.cpp:253-270`）：证书 **MD5/SHA1 原始字节**双指纹比对，全中则 `ignoreSslErrors()`，否则发 `checkSslCertifcate(errors)`（**保留原拼写**）并 `abort()`。

**QWebdav 三个调用点收口点（已由 conntest.cpp 逐个验证通过，尚未落到 vendor 源）**：① 含 `connect` 的函数体首行 `using ::connect;`；② 含 `disconnect` 的函数体首行 `using ::disconnect;`；③ 上述 sslErrors 签名收口。

**教训（勿再犯）**：本节一度凭印象断言「Qt3 `QObject` 无 `deleteLater()`」，**与事实不符**（Qt 3.5 `qobject.h:174` 就有），并据此造了多余的自删事件机制。已按 §13 纪律改为**逐条 `grep` 实测**再下结论。同批核验的其余断言（`QByteArray`=`QMemArray<char>`、`QString` 无 `size/chop/toUpper/clear/split(QChar)/toUtf8`、Qt3 无 `QScopedPointer`/`QRecursiveMutex`、`QIODevice` 非 QObject）**实测全部成立**，故 §7 判定结论不变。**今后凡写「Qt3 缺 X」，必须附实测命令与命中行。**

**Qt3 下 phonedb.cpp 调用点收口**（QT3_BUILD 分支）：`QIODevice::ReadOnly/WriteOnly`→`IO_*`、`QDir().mkpath`→`qMkdir(dir,true)`（用 compatcore34 重载避开 qglobaltype_shim 单参版二义）、`QByteArray::constData()`→`data()`、`QFile::write(QByteArray)`→`writeBlock(data,size)`、`QString::toUtf8()`→`utf8()`、`QString::size()`→`length()`、`QNetworkReply::finished` 无 QStringLiteral。
phonedb.h：Qt3 include `<qobject.h><qstring.h><qcstring.h>`；`Q_SIGNALS:` 占位→`signals:`（Qt3 无 Q_SIGNALS 宏）。
成员函数内 `connect(...)` 无限定名查找命中 `QObject::connect`（3 参，成员），**ADL 不并入全局模板**（gcc 实测）→ ensureData 函数体顶部 `using ::connect;`（QT3_BUILD 包裹）解决。

**Qt3 垫片行为修正（对拍暴露）**：
1. `QNetworkCookie::parseCookies`：对齐原生语义——**只解析首个 `name=value`**，其余 `;` 视为属性不产出新 cookie（原实现错切 3 个）。
2. `toRawForm()`：小写 `; domain=/; path=/; secure`（原生 Qt4/6 输出小写）。
3. `rawHeader/hasRawHeader`（Request 与 Reply）：改为 strcasecmp 大小写不敏感（原生语义）。
4. **QCString 尾 NUL**：Qt3 `QCString::size()` 含 NUL（`"abc"`→4），`QCString::resize(n)` 语义=内容 n-1+NUL，无法 resize 去 NUL。新增 `toCleanQBA()`（用 QMemArray 手工拷贝 content 部分，size()=内容长、无尾 NUL）统一所有对外 QByteArray 出口，否则依赖 size() 的 fromJson/trimmed/写入错位 1 字节。
5. `QNetworkReplyEvent` Set-Cookie 回写：`deliverResult` 里按 header 大小写不敏感找 `set-cookie` → `QNetworkCookieJar::setCookiesFromUrl`（跨请求会话）。
6. redirect 目标：`RedirectionTargetAttribute` 从 `location` 头（大小写不敏感）填充。
7. progress 回调 udata：`issue()` 传 `ReplyCtx*`（同 done），`qnamProgressCb` 原按 `QNetworkReply*` 强转——改为 `ReplyCtx->reply`。

**对拍**：`/tmp/opencode/qnam-test/`（独立于仓库）——协议层（无网络）同测试体 `run.sh [qt6|qt4|qt3]` 三端：Request rawHeader（含大小写不敏感）/attribute、Cookie parseCookies/toRawForm/jar 匹配、MultiPart 拼装。**三端 ALL PASS**（qt3 经 stub EventPoller 免真实网络依赖）。真实 HTTP 往返（GET/redirect/cookie 会话/abort）留集成层（真实 qlstik 的 phonedb 下载归属库）验证。

**收尾项**：① qnam_shim 扩展 Qt4 支援（把 QCString/QMemArray 依赖收敛），Qt4 重新挂载 phonedb；② 真实 HTTP 集成验证；③ davbisync/imageaiutil 等 QNAM 大模块（批次 3）挂载时复用 `using ::connect;` 模式。

### 6.3a 批次 2a 落地记录：davbisync_baseline 三个垫片（Qt3/Qt4 已全绿）

**版本核实更正**（计划原文"QSaveFile 仅 Qt3、Qt4.1+ 原生"有误）：QJson、QStandardPaths、QSaveFile 三个类均为 **Qt5.0/5.1 才引入**，Qt3.5.0 与 Qt4.8.7 的 QtCore 下都无对应头，故三个垫片对 Qt3 与 Qt4 **同时启用**（stikcommon.pri 用 `isEmpty(QT_VERSION)`=Qt3、`lessThan(QT_VERSION,5.0.0)`=Qt4 条件挂载 .cpp，Qt5+ 走原生、垫片不参与编译）。

**版本判据规整**（与 qlstik.pro 真实构建一致）：
- Qt3：qmake `isEmpty(QT_VERSION)` → `DEFINES += QT3_BUILD`（build-qt3/Makefile CXXFLAGS 已含 `-DQT3_BUILD`）；垫片头内 `#ifdef QT3_BUILD` 选 Qt3 小写头（`qstring.h`/`qcstring.h` 等）。
- Qt4/Qt6：无 `QT3_BUILD`；垫片内 `#if QT_VERSION < 0x050000` / `< 0x040000` 选分支。
- 跨版本调用点写法（davbisync_baseline.cpp 内）：
  `.cbegin/.cend`→`.constBegin/.constEnd`、`it.value()`→`*it`（Qt3 与 Qt6 的 QMap 迭代器都有 `operator*`）、`QString::size()`→`length()`、`QFileInfo::absolutePath()`→`qAbsPath()`（stikcommon/qglobaltype_shim.h）、`QDir().mkpath()`→`qMkdir()`、`QIODevice::ReadOnly`→`kBaselineReadMode` 常量（Qt3 映射 `IO_ReadOnly`）。

**对拍中暴露并修复的垫片缺陷**（qjson_shim.cpp，Qt4 垫片行为与 Qt6 原生逐项对照）：
1. `insert` 的 upsert 语义：原实现用 `cJSON_ReplaceItemInObjectCaseSensitive`，键不存在时**静默失败**（首次 insert 内容全丢）。修复：键存在→`ReplaceItemInObjectCaseSensitive`（自动重设 replacement 的 string 并删旧）；不存在→`cJSON_AddItemToObject`。
2. `QJsonValue(const char*)` 构造缺失：`QJsonValue("…")` 会把 `const char*` 隐式转 `bool`（输出 `true`）。修复：补该构造，空指针按 Qt 语义转 null。
3. 平台差异：`QJsonDocument::toJson` 的 Qt3 分支用 `QCString` 承载 cJSON 缓冲（Qt3 的 QByteArray 无 `(const char*)` 构造）；QMemArray 无 `append` 的对应处理已由测试桥内聚。

**对拍方法与结论**：`/tmp/opencode/qjson-test/`（独立于仓库，无污染）——同一测试体 `test.cpp` 零宏零版本分叉，经 `qjson_dispatch.h`（`__has_include` 探测原生 QJson 头）自动选实现，`run.sh [qt6|qt4|qt3]` 单入口三环境编译运行。判据与真实构建对齐：qt3 传 `-DQT3_BUILD`、链 `libqt-mt`；qt4 链 `libQtCore`；qt6 链 `libQt6Core`。13 项断言（往返、数值精度 1739200000000.0、Undefined/Null 区分、insert 覆盖、嵌套对象、BOM 剥离）**三端全绿**。

已知收窄差异（语义等价、自读自写无害）：垫片把空对象序列化为 `"cloud":null`，Qt6 原生为 `"cloud":{}`；解析回 `toObject()` 同为空，不影响 davbisync_baseline 基线读写。

**运行验证（批次 2a 验证门）：** `/tmp/opencode/baseline-run/`（`run.sh [qt6|qt4|qt3]`，同一驱动 `runonce.cpp`，跨版本文件访问经 `baseline_dispatch.h` 收敛）。驱动覆盖：
1. save（local/cloud 多键、`mtimeMsec=0` 无效肢）→ load 往返相等（qint64 毫秒精度）；
2. save 后数据目录无 `*.tmp*` 悬挂（QSaveFile 原子提交成功即 rename 清 tmp）；
3. re-save 覆盖路径后仍无 tmp 残留、可读回新增键；
4. `load` 只读：正常文件 load 前后字节快照一致；
5. 写坏 JSON → `load` 返回 false（不误报成功）。
三端（Qt3 垫片 / Qt4 垫片 / Qt6 原生）**全部 ALL PASS**。QSaveFile 的中断不毁语义由「tmp 悬挂分离 + 失败时旧文件不动」的 commit 实现保证（见 qsavefile_shim.cpp 注释），进程级 kill 注入暂未自动化。

顺带修复：`qstandardpaths_shim.cpp` 的 `shim_execBaseName()` 原用静态 `QCoreApplication::applicationFilePath()`，无实例时会打 Qt4 警告并回退空；改为显式判 `qApp`，无实例时直接返回空串（与 Qt 行为一致，警告消失）。

### 6.4 Qt 3.5 实测底座与垫片清单（批次 1 落地，Qt3 已全绿）

**底座纠正**：`/opt/qt338sh` 实为 **Qt 3.5.0**（目录名有误导），不是 3.3.8。逐头核实后，Qt 3.5 缺的不止 include，而是整类 API：

| 缺项 | Qt 3.5 现状 | 处置 |
|---|---|---|
| `QCoreApplication` | 无此类（Qt4 引入），`install/removeTranslator` 是非静态成员 | `stikcommon/qcoreapplication_shim.h`：同名类 + 静态包装走 `qApp`，**源码零改动** |
| `QVector<T>` | 是宏 `#define QVector QPtrVector`；缺 `append/removeAll/按值 contains/begin..end` | `stikcommon/qvector_shim.h`：`#undef` 后补同名派生类 |
| `QHash` | 无此类 | `stikcommon/qhash_shim.h`：QMap 派生，仅补 `operator[]` |
| `qUtf8Printable` | 无（Qt 5.10 才有） | `stikcommon/qstring_shim.h`：Qt3 用 `utf8().data()`，Qt4 用 `toUtf8().constData()` |
| `std::as_const` | 非 C++17 标准 | `stikcommon/stdcompat_shim.h`：`__cplusplus < 201703L` 时补 |
| `QSettings::value/setValue` | 只有 `readEntry/writeEntry`；且 `qapp.h` 已提前引入 `QSettings` 定义，**同名派生不可行** | 改调用点（`myi18n.cpp` 2 处 `#if`） |
| `QLocale::script()` | 无；同名派生同样被 `qapp.h` 挡住 | 改调用点（`myi18n.cpp` 1 处 `#if`，Qt3 恒回退 zh-CN） |
| `QMetaObject` | 无（`QObject::metaObject()` 是成员调用，垫片够不到） | 改调用点（`myi18n.cpp` 1 处 `#if`；Qt3 下页面重译交调用方触发） |
| `Qt 4.8` `QVector::removeAll` | 无（Qt5 起 `QVector=QList` 才有） | 改调用点（`myi18n.cpp` 1 处 `#if`） |
| `libobfuscate` | 需 relaxed constexpr（c++14）；`advobfuscator` 需 c++20 | `qlstik.pro` Qt4/5 底线 c++11→**c++14**（qmake 3.x 无按文件 CXXFLAGS）；`davobfus.cpp` 的 ADVobfuscator include 与 `using namespace` 按 `__cplusplus >= 202002L` 包裹 |

垫片一律**平铺在 `stikcommon/`**、按 Qt 类名取名（如 `qvector_shim.h`），不建 `compat/` 目录、不建聚合头、不用 `-include` 预包含；由使用方在自己的条件 include 分支里显式引入。

**不可垫片、必须改调用点**（Qt3/4 的真实硬边界，记录以免重复踩）：
`QSettings` / `QLocale`（定义被 `qapp.h` 抢先引入）、`QObject::metaObject()`（成员调用）、`QByteArray` 全套 Qt4 方法（Qt3 是 `typedef QMemArray<char>`，见 §8 批次 1 暂缓项）。

## 7. 可共享判定标准（阈值）

| 改动类型 | 允许上限 | 超限判定 |
|---|---|---|
| include / `#ifdef` 平台包裹 | ≤3 行/文件 | — |
| latin1 字面量 → `u'x'` / `QChar` / `QString::fromUtf8` | ≤50 行/文件且无语义改动 | 超出或触及逻辑 → 不可共享 |
| 控制流 / 数据结构 / 算法 / 错误处理 | **0 行** | 任意 1 行 → 不可共享 |

按此 `stickerstore` = 3 行 include + 40 行 latin1 = 43 行 → 判可共享。
