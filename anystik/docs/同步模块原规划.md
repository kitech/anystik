# 同步模块原规划（davbisync）

> 目的：记录同步模块**原定的规划目标、参考机制与边界**，作为实现与评审的基线。
> 资料口径：本文只写有真实出处的内容——来源分两类：
> **(A) 工程磁盘自身**：`src/davbisync.h`（编译器 `-fsyntax-only` 审查通过的真头声明）。
> **(B) rclone bisync 参考机制**：rclone 官方文档 `https://rclone.org/bisync/`、rclone 论坛 `#46636` 冲突机制复述、GitHub `rclone/rclone` 的 `cmd/bisync/` 源码树。

## 一、规划目标

做一个"连云盘的双向同步引擎"，让本机贴纸材料与云端（WebDAV）始终保持一致：

- **双向**：本机改动推到云端，云端改动拉回本机，两侧都算数；
- **可续、可中止**：中断不丢基线、可安全恢复；
- **不合并、不自动毁数据**：两侧同时产生冲突时，保留双方，交上层/用户裁决。

## 二、参考机制（rclone bisync）

原规划以 rclone `bisync`（双向同步）为机制参考，逐条对齐语义：

1. **基线（last sync）**：首次运行建立"两侧一致基线"（当下信任状态）；后续每次运行时，拿两侧当前清单与上次基线比对，得出"哪边新/哪边改/哪边删"。
2. **增量四态**：相对上次基线，单侧出现 新出现(new) / 较新(newer) / 较旧(older) / 被删除(delete) 即算出差异，
   不做全量。比较依据默认 size+modtime，可用 `--compare` 加 checksum；无 modtime 时只能判
   change/unchanged（无法区分 newer/older）。
3. **冲突判定**：同一文件**两侧都相对基线有变化** 且 当前两侧**不一致** = 冲突。
4. **冲突分类**：官方不设 conflict-newer/older/equal 并列态标签（旧 `..path1/..path2` 为 v1.66 前默认）。
   现代机制按 `--conflict-resolve` 决出胜方/败方：path1/path2/newer/older/larger/smaller；
   无法裁定（如两侧 modtime 相同）即无胜方，双方都保留。
5. **冲突处置（--conflict-loser，默认 num）**：分出胜方与败方；默认给败方加序号后缀 `.conflictN`（**保留双方，不删任何一侧**）；`delete` 模式才删败方只留胜方（须配 `--backup-dir` 兜底）。原规划**不采纳自动删败方**，默认保留双方。
6. **自动裁决开关（--conflict-resolve）**：冲突时可自动偏向 本机/远端/较新/较大 等；原规划**保留手动口子**，不默认自动裁定。
7. **门卫（--check-access）**：同步前**校验**两侧对应位置都存在同名探测文件（默认 `RCLONE_TEST`）。
   探测文件**不会被自动创建**——须预先放置（`rclone touch/copyto`，或先跑一次不带该开关的运行建立匹配）。
   校验不过即中止，防路径/配置配错导致自毁式误删。
8. **崩溃自愈（--recover）与优雅停机（SIGINT/Ctrl+C）**：异常中断后，基线 listings 被视为不可信而作废；`--recover` 回退到**最近一次成功运行的备份基线**自动续跑，免全量重来。规划里"中止须可恢复、不毁基线"即对应此义。
9. **首次重基线（--resync）**：两侧长期不同步或基线丢失后，用 `--resync` 一次性以一方为准重建一致基线。本工程统一逻辑下对应**状态文件缺失 = 空列表**：不做专门重扫，首次运行即按统一 diff 双向往返。
10. **防过量删除（--max-delete，默认 50%）**：任一侧删除比例超限立即中止，防网络故障/误删引发灾难性清空。
11. **空路径保护**：非 resync 运行任一侧 listing 为空即拒绝同步（"Cannot sync to an empty directory"），防意外清空另一侧。
12. **过滤变更防护（--filters-file）**：过滤文件变更后强制 `--resync`，防新过滤规则把被排除文件误判为"删除"。
13. **v1.64+ 相等性预检**：冲突改名/复制前先比对两侧当前内容，相同则不算冲突（显著降低假冲突）。

### 参考机制的真实教训（冲突排查口子）

> 冲突频繁时常是"假变化"：云端后端（如 s3/idrive）把 modtime 或哈希报得比上次基线新、而内容其实没变，导致 bisync 误判每侧都"变了"而狂出冲突。排查方向：查事件日志确认云端是否真变 → 查 `--recover/--resync` 是否造成假基线 → 用非 s3 后端最小复现。
>
> （rclone 论坛 bisync 冲突案例 + bisync 文档 `--recover` 语义）

**本工程对应**：引擎的诊断（冲突/跳过清单）即为支撑这类排查留的口子：先确认云端是否真变，再查是否 `abort()` 中断造成假基线，最后缩小到最小可复现。

## 三、本工程原规划功能

### 3.1 同步方式（统一双向，无模式区分）

不再区分 Full/Incremental/Reverse：同步按钮 = **单一双向逻辑**（rclone bisync 默认 `conflict-resolve none` + `conflict-loser num`）。`SyncBaseline` 状态文件只作「每侧相对上次是否变化」的参照——**状态文件不存在 = 状态列表为空**（空 map），不设任何首次/全量特判分支；空状态下凡「两侧都有且不相一致」的条目因双侧均无状态记录 → 双双判为新增且走冲突双保留。

### 3.2 贴纸包参与策略（PackPolicy）

每个贴纸包一个策略开关组，决定该包是否参与同步、如何参与：

- 是否从云端拉取（pull）；
- 是否推送云端（push）；
- 服务器端相对云盘根的贴纸目录（空 = 不参与）；
- 贴纸包描述；
- 是否覆盖远端已有文件。

内联判定：参与 = 拉 或 推 至少其一；云端根目录 = 指定目录非空则用它，否则回退默认。

### 3.3 同步诊断（SyncDiagnosis）

单次同步的诊断报告：

- 冲突清单（两侧同时变更且不一致的文件）；
- 被跳过清单；
- 各贴纸包参与策略表；
- 引擎就绪标志 + 引擎错误描述。

内联计数：冲突数、待处理数（冲突 + 跳过）。

### 3.4 同步引擎（SyncEngine）

公开 API（对照真头声明）：

- 云可用性探测；
- 写入连接设置（连接类型/主机/根路径/用户名/密码/端口/是否SSL）；
- 启动同步（默认全量，可指定方式）；
- 中止；
- 运行中判断；
- 进度百分比。

信号：进度更新 / 日志行 / 完成（退出码+摘要) / 目录树扫描完（文件数+目录数)；
槽：设置轮询延迟。

内部：运行中/已暂停/进度百分比 状态 + 连接设置成员 + WebDAV 连接对象与目录解析器（均 vendored 真类）。

**里程碑（对齐 rclone bisync 语义）**：

- **M1 基线固化（状态基准）**：listing 快照落盘（JSON，记录 size/modtime）；不区分全量/增量——状态文件缺失即空列表，首次运行按统一 diff 双向往返（无 bisync `--resync` 概念）；
- **M2 统一双向 diff**：当前清单 ↔ 状态列表逐侧对比（缺失条目判定为变化），无 new/newer/older/deleted 四态——只剩 新增/已变/一致 三态 + 不做删除；
- **M3 冲突与诊断**：双侧皆变且 size 不一致 = 冲突（新状态均无记录也判为变）→ 填充 SyncDiagnosis 的冲突/跳过清单；
- **M4（已取消）**：不再有独立反向回灌；统一双向逻辑已覆盖云端→本地下拉与本地→云端上传两个方向；
- **M5 PackPolicy 接入**：按贴纸包 pull/push/目录/覆盖策略决定参与与否；
- **M6 护栏**：check-access 校验（不自动建探测文件）、max-delete 防过量删除、空路径保护、中断基线安全（abort 不毁基线）。

**首期 Push 实现明细（2026-09-12）**：

- 内置源判定：`StickerStore::isBuiltinSourcePack(packId)`，用 `downloadedPackMeta/<packId>.url` 与 `kBuiltinSources[].url` 归一化（剥 `https://gh-proxy.com/` 前缀，防止换代理使匹配失效）比对；无 url（如「粘贴板」）→ 判为参与上传。
- **内置源排除（两侧对称）**：上传侧按 packId 整包不列入清单 → 不 mkdir、不上传；下载侧用 `StickerStore::builtinSourceCloudDirs()`（全部内置源包的 `sanitizeDirName(title)` 集合）在 `ensurePack` 前按云目录名拦截 → 不为其建包、跳过拉取。内置源目录整体不参与同步，与 title 是否被 sanitize 转义无关。
- 上传核对（首期 `--size-only` 语义；后续升级为 size+mtime 双值判定，见下「双向同步增补核对」）：对每个本地文件先 HEAD 云端路径；404（ContentNotFound）→ 上传；200 → 读 Content-Length 与本地 size 比对 → 一致跳过、缺失/不同以本地覆盖。
- 目录处理：每个云包目录首次出现时 `mkdir`（任意结果都继续，已存在容错交给后续 HEAD/put 兜底）。
- 中止语义：任一网络错误 / HTTP≥400 / 本地文件丢失 → 停止并保留已上传部分；每文件均独立核对，重跑可续传不重传。
- 进度：`uploadProgress` 按文件推进、文件内按字节并入 percent；按钮文字/信号驱动。尚未做本地删除传播与云端新文件拉取。
- 同步进度窗口（`SyncProgressPopup`，QskPopup 浮动层，参照下载/重命名弹窗）：首页「同步」按钮懒创建并 `open()`。运行中禁用「关闭」、可用「取消」（`SyncEngine::abort()`，经 finished=2 收尾）；`finished` 后显示成功绿/失败红/已取消橙摘要。实时结构化日志：时间戳 + `[tag]`（scan/pack/mkdir/upload/sync/webdav）+ 级别配色（Info/Warn/Error），自动滚底；过滤 = 级别下拉（全部/Info/Warn/Error）+ 关键词(150ms 防抖，匹配 tag+line，大小写不敏感)；「复制当前结果」把过滤命中的行合并为纯文本写入系统剪贴板；「清空」清空本次会话日志。日志存于窗口私有 LogModel 实例（不污染全局日志），`LogModel` 构造函数改为公开以支持独立实例。
- 同步引擎日志信号：`logLine(QString)` → `syncLog(int level, const QString& tag, const QString& line)`，level 取 `davbisync::LogLevel`（Info/Warn/Error），全部 emit 走统一 `log()` helper。
- 实时传输统计：进度行 detail（`statDetail()`）实时刷新「第 N/M · 文件名 · 大小 · 本文件已用 s · 总用时 s · 余约 s（ETA，按文件数线性外推）」，由窗口 m_detailLabel 展示；每文件开始时日志输出「上传 <名> · <大小> · 第 i/N」，完成后「完成 <名> · 用时 X s」。统计成员：m_startMsec/m_fileStartMsec/m_lastFileMs/m_etaSecs；下载方向复用同套统计。
- 环境注记：系统 `/usr/lib` 若存在更新版 Qt6 未版本化 `.so`，QSkinny 导入目标带来的 `-lQt6*` 会被 ld 误解析为错误 Qt；CMake 已把 vendored Qt 库目录（`Qt6_DIR` 推导）前置 `-L`（非 Android 分支）。

**双向同步（M1–M6）实现（2026-09-12 核对）**：

- **M0 StickerStore 下行落地**（`src/stickerstore.h/.cpp`）：`sanitizeDirName`（原 davbisync normalizeDirName 移为公开静态，双向共用）、`ensurePack(title)`（复用 findOrCreatePack）、`importStickerFile(packId, srcAbs)`（云下载临时文件移入 `base/packs/<title>/` + QImageReader 预检 + add_sticker，同包同相对路径已有行则幂等返回 true）、`renameStickerFile`（冲突改名：物理文件 + `UPDATE stickers SET file_path`）；`resolveStickerPath` 由 private 转 public（双向清单需要绝对路径）。
- **M1 基线固化**（`src/davbisync_baseline.h/.cpp`，已入 CMake）：JSON `AppLocalDataLocation/davbisync_baseline.json`，字段 `schemaVersion/lastMode/lastRunMsec/local{relPath:{s,m}}/cloud{...}`；写入用 `QSaveFile` 原子提交（tmp+rename，中断/崩溃不毁旧基线）。基线仅在全部成功（finishOk）时保存。
- **M2 双向增量 + 应用**：阶段 A 本地清单（packs+stickers → 云相对路径，size+mtime stat）→ 阶段 B 云端清单（`QWebdavDirParser::listDirectory` 逐目录 BFS 状态机，canonicalRel 归一化剥前导/尾随斜杠）→ 阶段 C `buildOpQueue` diff → 阶段 D 应用（mkdir/HEAD 核对/put 上传、get 到临时文件 → importStickerFile 下载）。**无删除方向**：delta 只有 new/changed/same，云端多余/本地多余均保留。
- **M3 冲突与诊断**：统一逻辑下用「size + 双侧均有效的 mtime」双判据判断每侧是否变化（任一侧 mtime 无效(0) → 自动回退 size-only；缺状态文件时所有条目视为新增）；双侧皆变且当前不一致（size 不同，或 size 同但双侧 mtime 有效且不同） = 冲突 → 参考 rclone 默认 `conflict-resolve none` + `conflict-loser num`：云端旧版 `move` 改名 `file.conflict1/.conflict2…`（自动编号，查重已存在与本次已分配名），本地新版本上传覆盖原 rel；本地侧旧版已不存在（本地 changed 即当前文件为新版），数据双版本分别保留在云端（.conflictN 旧版）与本地上传（新版）。冲突经 `syncLog(tag=conflict)` 与 `SyncDiagnosis.conflicts`（含两侧 size 与处置名）暴露。mtime 判据只做「变了没」追踪、不裁定 newer/older——冲突处置无 mtime 倾向（默认 whence 语义，等价落回本地优先覆盖），rclone 的 `--conflict-resolve newer/older` 口子不采用。`SyncDiagnosis` 已真填充 conflicts/skipped。
- **M4（已取消）**：不再有独立的反向回灌；`startSync()` 为无参单一路径，双向方向（上传/下载/冲突）由 diff 统一决定，无 lastMode=reverse 概念。
- **M5 PackPolicy 接入**：`setPackPolicies(QMap<packId, PackPolicy>)`（空 map = 默认全参与）；pushEnabled=false → 该包不上传；pullEnabled=false → 该包不下载；两者皆关 → 整包跳过并记诊断；云目录用 `policy.cloudRoot()`（stickerDirRel 非空时生效）。内置源包依旧全局排除。
- **M6 护栏（简化）**：因「不做删除」，`max-delete`/空路径保护不适用；abort 与崩溃均不毁基线（仅成功时原子写）；反删方向不实现。check-access 探测文件机制保留为文档中的未来可选开关，本期不实现。
- **云根** = `davUrl.path()/anystik/`（写死，`davbisync.h` `m_cloudRoot = "anystik"`，与 `PackPolicy::cloudRoot()` 默认一致）；其下直接放各贴纸包目录 `anystik/<title>/`。`anystik` 层由统一 mkdir 链按需逐层 MKCOL，重扫/重根切换无独立概念，一切按统一 diff 处理。

**双向同步增补核对（2026-09-12；mtime 第二判据 + 能力检测 + 修复）**：

- **mtime 第二判据（不再仅 size-only）**：changed = `size 不同 ||（双侧 mtime 均有效(≠0) 且不同）`；任一侧 mtime 无效(0) 自动回退 size-only（兼容无 mtime 服务器）。相等预检 = size 同 且（任一 mtime 无效 || mtime 相同）才 skip；相等预检不过（size 同但双侧 mtime 有效且不同）→ 落入 lc/cc 判卷。
- **远程 mtime 只读**：`uploadFile` 的 `put()` 不再传 dt（默认 `QDateTime()` 无效 → qwebdav 不 set Date 头），远端 last-modified 不被上传方改写。需要对齐 mtime 时只落本地：下载完成后 `QFile::setFileTime(云mtime, FileModificationTime)` 设本地文件 mtime = 云 last-modified，消除下一轮误判空转。
- **写后回读**：PUT 响应 `Last-Modified`（RFC2822）解析成功 → 当轮回填真实云 mtime；失败置 0，下一轮扫描回填（不回读当轮再传，用户认可）。HEAD 幂等判定中云 mtime 与**基线**比（`m_cloudFiles.value(cloudPath).mtimeMsec`），不跟本地直接比——服务器写入时刻 ≠ 本地 mtime，互比会每轮空转重传。
- **能力检测（零阻断，专门探测未被 `DAV:` 类声明覆盖/规避非标准 Warn）**：getlastmodified 支持（目录扫描）、PUT 写后回读（首传探测）、OPTIONS 预检（读 Server/DAV:/Allow 头；`QWebdav::options()` 新增，走 `sendCustomRequest(req, "OPTIONS")`）。结果经 `remoteFeature` 信号 → 进度窗口新增 feature 行。**feature 行显示效果（人话化，值保留）**：`远程特征: 服务器软件: <名> · WebDAV 等级: 1(文件读写)+2(文件锁) · 可用方法: <GET/PUT/MKCOL…> | 文件时间: 支持✓/不支持✗ · 上传回读: ✓/✗(下轮回填) · 判定: 大小＋时间/仅大小`——DAV 等级原始值（如 `1, 2`）转译为括号人话、判定词去掉“时间戳/兼容”等术语（服务器软件 · WebDAV 等级 · 可用方法 · 文件时间 · 上传回读 · 判定）。
- **HEAD 双值幂等（checkAndUpload）**：读 size + Last-Modified；skip 当且仅当「大小相同 且 云端相对基线未变 且 本地相对基线未变」——基线提升为成员 `m_base`（`startSync` 载入一次，`buildOpQueue` 与 `checkAndUpload` 同源）；纯 size-only 服务器（两侧 mtime 均为 0）且大小一致 → skip 兼容；扫描有 mtime 但 HEAD 不回 → 保守上传不吞变更。
- **修复记录（本次核对发现）**：① downloadFile 内置源跳过分支原不推进 `m_downloadIndex` → 无限循环；改 `++m_downloadSkipped; ++m_downloadIndex; emitProgress(); pushNext();`。② 跳过计数拆分为 `m_uploadSkipped`/`m_downloadSkipped`（相等预检、HEAD 幂等归上传侧；下载政策 skip 与 builtin skip 归下载侧），`finishOk` 摘要合并展示「uploaded X, skipped Y, downloaded Z」。
- **多客户端共享同一 dav 目录**：冲突保留文件按 `x.conflict<数字>`（rclone num 风格）过滤——本地与云端两侧 listing 均在 diff 前剔除，不下载/不上传/不进基线，仅记诊断「跳过」，防另一台机器把冲突保留文件下载“转正”再上传传播。并发边界：无锁，同一文件并发写 = 后写覆盖（last-write-wins，与 rclone bisync 同级）；并发冲突 rename 竞态 = 一方 move 失败仅 Warn 自愈（云端至少保留一份 .conflictN，不丢数据）；每机基线从各自本地 JSON 读取、互相独立，云清单实时共享。
- **云目录名 = 本地 db 目录名（不再转译 title）**：上传侧云目录取该包 sticker 的 `file_path` 目录末段（如「剪贴板」包本地为 `pastes/` → 云端 `anystik/pastes/`，不再用 `sanitizeDirName(title)` 生成「粘贴板」）；空包兜底 `sanitizeDirName(title)`。下载侧目标包优先用本机已有云目录映射 `m_localDirPacks`（剪贴板新文件归原包，目录名两端一致），新机器无映射才以云目录段为标题建包。旧规则遗留的云端历史目录（如 `anystik/粘贴板/`）不再被本机 rel 覆盖，会被视作云新增拉回；引擎无删除方向，需时手动清理云端。

## 四、边界（原规划明确不做的）

- **不做内容合并**（无规则可自动合并，rclone bisync 同样不做）；
- **不自动删除败方**（默认保留双方冲突件）；
- **不自动裁定冲突赢家**（仅报告，交上层策略/用户）；
- **状态文件缺失 = 空列表**：不做专门首建/`--resync`——首次运行即按统一 diff 双向往返（两侧均存在且不相一致 → 冲突双保留）；
- **不自动创建 check-access 探测文件**（rclone 同样只校验、不生成，须预先放置 `RCLONE_TEST`）；
- **不做任何删除方向**（2026-09-12 确认）：同步只增改、永不删除文件——云端多余文件与本地多余文件一律保留，删除由用户在任一侧手动完成，引擎不传播。因无删除，`max-delete`、空路径保护、`--recover` 基线回退等仅在"删除语义"下有意义的护栏不适用；abort/崩溃经原子基线写入自然不毁数据。

## 五、依赖（vendored QtWebDAV）

WebDAV 传输层采用 vendored QtWebDAV v2.1（`vendor/qwebdav/`）：`QWebdav`（连接/传输）、`QWebdavDirParser`（目录解析）、`QWebdavItem`（条目）。已接入工程 CMake 构建源表与 Qt6::Xml 链接。另新增 `options()` 封装（`sendCustomRequest(req, "OPTIONS")`），供同步引擎 OPTIONS 预检探测 Server/DAV:/Allow 头。
